# 同步边界与本地缓存

本文记录 v1 客户端当前强制执行的边界，以及发布前仍需在真实设备和 Gitee 私有沙箱中测量的项目。

## 已实现边界

| 项目 | v1 行为 |
| --- | --- |
| 单个图片资产 | 最大 10 MiB；超限时拒绝发布，不自动压缩 |
| Gitee commit 分页 | 每页 100 条 |
| 增量拉取 | 分页遍历到精确 checkpoint 或仓库根；分页不前进时停止，不按时间或固定页数猜测 |
| 模糊成功恢复 | 分页遍历到仓库根并精确匹配 batch trailer；分页不前进时暂停，不重新提交 |
| 单轮推送 | 最多处理 20 个批次，后续由同一档案的唯一 Worker 继续 |
| 同步并发 | 每个档案一个串行 WorkManager 任务，不跨档案消费 Outbox |
| 429 | 遵守服务端 `Retry-After`，并与本地指数退避取较晚时间 |
| 日期 | note、event 和 asset 必须位于真实 `YYYY-MM-DD` 日期目录；note/event 按档案固定时区核对 |

真实 Gitee 多文件请求的有效载荷、账号级限流和分页响应仍由 OpenSpec 任务 `1.5` 的专用私有沙箱合约决定。在取得该证据前，不提高资产上限或把 Gitee 未公布的限制写死为兼容承诺。

## 缓存策略

Android 为每个档案维护内容寻址图片缓存和不可变 Markdown revision 缓存。配置页显示两类缓存合计的文件数和字节数。

“清理可重建缓存”只处理：

- 原子写入遗留的临时文件；
- Room 中没有引用的孤立文件；
- 引用计数为零的图片资产；
- 不再被任何 `NoteRevision` 行引用的 Markdown 文件。

该操作不删除活动笔记、归档 revision、待推送 Outbox、checkpoint 或 Gitee 历史。引用中的图片即使理论上可从远端下载，也不会仅为了腾出空间而删除，避免离线阅读退化。

## 待测性能门槛

以下结果需要 release 构建、代表性中低端 Android 真机和专用 Gitee 沙箱，当前不宣称已经通过：

- 大仓库首次完整树下载、校验和 Room 重建的耗时及峰值内存；
- 10 KiB、100 KiB 和 1 MiB Markdown 的编辑/预览首帧和滚动性能；
- 大量图片缓存扫描、清理和缺失图片修复性能；
- 至少 10,000 revision/event 的确定性投影耗时；
- Gitee 多文件 commit 的有效请求体大小、429 窗口和二进制 Base64 开销。

测量报告至少记录设备型号、Android 版本、构建类型、数据规模、P50/P95 耗时、峰值内存、网络条件和 Gitee 响应头。未完成这些测量前，OpenSpec `11.6` 保持未完成。
